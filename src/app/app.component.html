AEM Fragment Embed

Embeddable AEM content fragments — custom element + Shadow DOM, drop into any HTML page

Two apps that solve opposite directions of the same integration problem: the first two tabs pull EDS-authored content into this non-EDS app, the third ships this app's UI out as a custom element an AEM DA block loads.

⚠️ These embeds use a lightweight loader instead of the stock aem-embed.js: the source project's own scripts.js bootstraps AEM Commerce config and assumes it owns the page, which throws when run inside a foreign host. Also note the source project (main--vwr--ynaka-adobe.aem.page) does not currently send an access-control-allow-origin header, so the fetches below may fail with a CORS error in the browser console unless you've enabled it (e.g. via a CORS-unblocking extension, or on the source project itself). See the README for details and the real fix.

Pulls EDS-authored content into this non-EDS app. It loads <fragment-embed>, a custom element defined in /scripts/fragment-embed.js, built following the aem-embed pattern (custom element + Shadow DOM, driven by a single url attribute). It fetches the fragment's .plain.html inside a Shadow DOM and loads the matching block's CSS/JS (/blocks/hero-lab/hero-lab.js and .css).

The same inbound direction, and the same <fragment-embed> element, pointed at a different fragment/block pair to show it's not hero-lab-specific: fragments/card-fragment (served from the .aem.live domain) using the blocks/cards-category block.

The opposite direction: this ships an app-built UI out as a custom element that an AEM DA mfe block loads. projects/vwr-header-mfe is a standalone, zoneless Angular Elements bundle that registers <vwr-header-mfe>. It is a separate build target (npm run build -- vwr-header-mfe → dist/vwr-header-mfe/browser/main.js) and is meant to be await import()ed by that block, not by this workspace's own app. If you want a Spartacus-style header or footer inside AEM, this is the sample to copy.

Two non-obvious contracts make it work. The block does await import(scriptUrl) and then immediately document.createElement(tagName), so customElements.define must already have run when the import promise resolves — which is why main.ts uses top-level await rather than a fire-and-forget (async () => {{ '{' }}…{{ '}' }})(), since a dynamic import resolves on top-level execution and does not wait for an async IIFE's internal awaits. It also guards registration with if (!customElements.get(TAG_NAME)) so a second import is a harmless no-op instead of a duplicate-definition error.
